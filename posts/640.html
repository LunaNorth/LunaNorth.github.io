对比项 List<Type> 版 Dictionary<string, Type> 版

2.3 几个关键 API

① ​​TryGetValue​​ ** 而不是 ​​ContainsKey​​ ** + 索引器

ContainsKey 之后再取一次，是两次哈希运算；更重要的是，如果中间有别的线程改了这个字典，”判断有”和”真的取”之间可能变化，会导致异常。TryGetValue 是原子的。

② ​​Activator.CreateInstance(type)​

运行时按 Type 创建对象，等价于 new SubWindow()，但类名是变量。它要求目标类有公共无参构造函数——SubWindow 默认就有（你没写构造函数时编译器会送你一个）。

③ ​​where T : Window, new()​​ ** 这对约束**

  • T : Window：编译期就能保证传进来的一定是窗口，后面 (Window) 强转绝不会失败。
  • new()：保证有公共无参构造，Activator 才创建得出来。

代价是：如果某个窗口只写了带参数的构造函数，就不能用这个泛型注册了。这也是为什么窗口类通常保留一个无参构造，数据通过 DataContext 传。

三、DataContext：Binding 到底去哪找属性

这是整个 MVVM 里最容易糊掉的一环，但规则只有一条：

​{Binding X}​​ ** 中的 X，是在当前元素向上找到的 ​​DataContext​​ ** 对象里，找名为 X 的属性。

两种写法效果完全一样，DataContext 里放的都是一个 MainViewModel 实例。

绑定生效的完整链条：

  1. MainWindow 的 DataContext 是一个 MainViewModel 实例；
  2. 子元素（TextBox）没有自己的 DataContext，就继承父级的；
  3. {Binding SendText} 于是在 MainViewModel 里找名为 SendText 的公共属性；
  4. 找到就建立通道，两边的值互相同步。

6.1 两个按钮，靠三个属性管住

属性 作用
IsDefault="True" 按回车等于点这个按钮

十一、面试题

题 1：WindowProvider 属于什么设计模式？它解决了 MVVM 的什么痛点？

解析：

它本质是服务定位器（Service Locator） ，也可看作一种抽象工厂——调用方只提供 key，由它负责实例化并返回。在 MVVM 里，它的作用是切断 ViewModel 对 View 的编译期依赖，让 VM 可以在没有 UI 的环境下被单元测试。更”正统”的替代方案是依赖注入（DI）容器，把 IWindowService 接口注入构造函数，好处是依赖关系显式、可被 Mock 替换；WindowProvider 这种静态类写法胜在简单，适合小项目。

题 2：DataContext 和 Binding 是什么关系？为什么绑定失败不抛异常？

解析：

DataContext 是”数据源”，Binding 是”按路径取值”。WPF 沿着可视化树向上查找最近的 DataContext，然后按 Path 反射取属性；找不到时不会抛异常，因为绑定在 WPF 里被视为”运行时约定”，失败只是让值保持默认，同时向 Trace 输出一条 BindingExpression path error。这种设计让 XAML 可以在设计时没有数据的情况下正常渲染，代价是排错要靠输出窗口。想让错误可见，可以设 PresentationTraceSources.TraceLevel=High 或监听 Validation.Error。

题 3：为什么 Show() 打开的窗口设置 DialogResult 会抛异常？

解析：

DialogResult 的语义是”模态对话框的返回值”，它必须有一个正在等待结果的调用方。Show() 是非阻塞的，调用方早已返回，没有”返回值”的接收者，因此 WPF 规定此时 DialogResult 必须为 null，一旦赋非 null 值就抛 InvalidOperationException。只有 ShowDialog() 会挂起调用栈并等待，才能承载这个返回值——这也是它返回 bool? 的原因。
