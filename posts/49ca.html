1. MvvmLight框架中的SimpleIoc对象使用

1. 本节目标

在一个最小控制台项目里完成三件事：注册接口、按接口取对象、观察两次取到的是不是同一个实例。

2. 一句话原理

6. 第三步：连接登记表和获取动作

这一段只做四步，顺序不要乱：

  1. SimpleIoc.Default：拿到应用默认容器。
  2. Reset()：清空上一次留下的登记和缓存。它适合示例和测试开头，正式程序不要随便清空别人注册好的服务。

7. 关键代码逐段看

代码 为什么这样写
SimpleIoc.Default 先拿默认容器，避免一开始就创建多个互不相干的容器
Register<IMessageService, MessageService>() 第一个泛型参数写“别人要什么”，第二个写“实际创建谁”
GetInstance<IMessageService>() 只暴露接口，调用者不需要知道 MessageService 的构造细节
first == second 用引用比较验证默认缓存是否生效
Reset() 保证本次示例从干净状态开始，避免上一次运行残留影响结果

为什么先写接口，不直接写 new MessageService()？因为一旦调用者直接 new，它就和具体类绑死了。以后换成 TimeMessageService 时，所有 new 的地方都要改；如果只依赖接口，通常只改注册那一行。

2. IoC容器对象项目结构的影响

1. 本节目标

新建一个最小 WPF 项目，让窗口只负责显示，把“创建 ViewModel 和准备服务”的工作移到 App 这个组合根。

2. 一句话原理

把 WPF 项目想成一家餐厅：App 是店长，负责安排厨师和服务员；MainWindow 是餐桌，只负责把菜端给客人看；MainViewModel 是菜单上的内容，不负责去后厨招人。

5 ViewModels/MainViewModel.cs 构造函数 接收 IMessageService
6 App.xaml Application 标签 删除 StartupUri
7 App.xaml.cs App.OnStartup 注册服务、创建窗口、交 DataContext

13. 小结与迁移

IoC 对项目结构最大的影响，是把“谁创建对象”从各个窗口和 ViewModel 里搬到了 App 这样的组合根。以后你新建页面时，可以先问：这个页面的 ViewModel 应该由谁创建？如果答案是“统一入口”，就把注册放到组合根，把 DataContext 交给页面。

4. IoC概念理解与自定义IoC容器

1. 本节目标

不借助 SimpleIoc，自己写一个只有“登记”和“解析”的最小容器 MiniContainer，并用它取到一个消息服务。

2. 一句话原理

3 Program.cs Main 注册接口并解析

传统写法是调用者自己创建依赖：

7. 关键代码逐段看

代码 意思
Dictionary<Type, Func<object>> 类型到“创建函数”的登记表

为什么用 Func<object>，不直接存对象？因为注册时还不应该创建对象；等到 Resolve 时才创建，才能控制创建时机，也方便以后加入缓存。

  • MiniContainer 里有 Dictionary<Type, Func<object>>。
  • Register 的第一个泛型参数是接口。
  • Resolve<T>() 能返回实现类。
  • 运行后输出问候文字。
  • 能说出“登记”和“创建”不是同一件事。

11. 常见错误

现象 原因 解决
找不到 Type 或 Func 没写 using System; 补上命名空间
提示 key 不存在 没先注册就 Resolve 先 Register，再解析
提示没有无参构造函数 Activator.CreateInstance 的限制 第 5 章改成构造函数注入
泛型顺序写反 接口和实现写反 第一个接口，第二个实现

  2. 故意不注册 IMessageService，观察异常。
  3. 思考：为什么 Resolve<T>() 需要把结果强制转换成 T？

13. 小结与迁移

IoC 不是框架专属名词。只要把“创建对象”的职责从调用者手里拿走，交给一个统一入口，就已经用上了 IoC。MiniContainer 很小，但已经具备“登记”和“解析”两个核心动作。

5. 自定义IoC容器的基本控制逻辑

1. 本节目标

把第 4 章的 MiniContainer 升级成能缓存单例、递归处理构造函数参数、检测循环依赖、清理登记和缓存的版本，并观察真实输出。

2. 一句话原理

一个能用的容器至少要有三块：登记表决定“怎么建”，缓存决定“建过没有”，创建逻辑决定“参数从哪里来”。再加一个“出错时能说清楚”的检查，就不会出现悄悄塞 null 的情况。

3. 要改哪里

3 Ioc/MiniContainer.cs CreateInstance 读取构造函数参数并递归解析
4 Ioc/MiniContainer.cs 方法区 增加 Unregister、Reset、InjectProperties
5 Program.cs Main 验证单例、注入、清理和属性注入

7. 关键代码逐段看

代码 意思
_singletons 已经创建过的对象，按类型缓存
_creating 当前正在创建的类型，用来发现循环依赖
TryGetValue 先看有没有缓存或登记，避免直接索引抛异常
GetParameters() 拿到构造函数需要哪些参数
Select(parameter => Resolve(...)) 对每个参数继续解析
constructor.Invoke(parameters) 用准备好的参数创建对象
Unregister<T>() 移除登记，同时移除它的缓存
Reset() 清空全部登记、缓存和创建状态

参考项目的 ZhaoxiIoc 是教学版，能帮助理解思路，但直接扩展时要注意几个点：

参考项目写法 容易出现的现象 本笔记的推荐写法
_instenceDic.Add(...) 重复注册会抛异常 用索引器赋值，后注册覆盖前一个
Resolve<T> 只查 _instenceDic _objectsDic 实际没有参与解析 只保留一张创建登记表
缺依赖时 objects.Add(null) 错误延迟到业务代码才出现 未注册就直接抛出明确异常
只处理构造函数的第一层参数 多层依赖不能稳定创建 Resolve 递归处理参数
App 和 ViewModelCenter 都注册 重复注册、职责不清 只保留一个组合根

13. 小结与迁移

自定义容器的基本控制逻辑就是：登记、解析、缓存、递归注入、清理和报错。SimpleIoc 比 MiniContainer 多了键值注册、工厂、生命周期等能力，但核心思想相同。以后看到任何 IoC 容器，都可以先找这五样东西。
