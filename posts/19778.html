绑定这条路上，值会经过四道处理，每一道都可能改变它，也都可能失败。

1. 系统默认 ValueConverter

本节目标

  • 弄明白不写转换器时，WPF 到底做了什么。
  • 知道哪些类型能自动转成文字，哪些不能。
  • 知道界面上的字符串什么时候能写回强类型来源，什么时候不能。
  • 学会用「默认转换」省掉一大半本来要手写的转换器。

1.1 不写转换器，值也能显示出来

先把最容易误解的一点说清楚：转换器不是必需品。 一个绑定不写 Converter，值照样能显示在界面上。

Salary 是 decimal，TextBlock.Text 是 string，类型明明不一样，为什么能显示？

因为绑定在中间偷偷做了一次转换。WPF 内部有一套叫 DefaultValueConverter 的机制：当来源值和目标属性的类型不一致时，它会去找一个合适的办法把值转过去。

找办法的顺序是：

  1. 如果来源类型和目标类型能直接赋值（比如都是 object），原样传过去。
  2. 如果来源类型自己注册过 TypeConverter，就用它。
  3. 如果目标类型注册过 TypeConverter，用它反向转。
  4. 如果来源类型和目标类型之间有 Nullable<T> 的关系，做包装或拆包。
  5. 都不行，就用 Convert.ChangeType 硬转一次。
  6. 还是不行，就报一次绑定错误，目标保持原值。

图 2：默认转换按顺序尝试六种办法，前一种不行才试下一种。

这套机制的存在，意味着你写界面时可以先不写转换器，等到确实转不过去了再加。

1.2 来源 → 文字：几乎什么都能显示

先看「来源 → 目标」这个方向。把一个类型不明的值送到 TextBlock.Text 上，会得到什么？

实测结果如下（TextBlock.Text，元素 Language 为 en-US）：

来源值 显示结果
double 1234.5 1234.5
int 42 42
decimal 19.99 19.99
bool true True
DateTime 2026-10-20 10/20/2026 12:00:00 AM
Visibility.Hidden Hidden
字符串 Red Red
自定义结构体（无 TypeConverter） 12.5 kg（走 ToString()）
自定义结构体（有 TypeConverter） 12.5 kg（自定义 TypeConverter）
null 空白

几个值得注意的地方：

第一，数字的格式跟随元素 ​​Language​​ ，但不是全部跟随。 这一点我实测时先想错了，特意验证了三轮，结论如下：

值 Language=en-US Language=zh-CN Language=de-DE
1234.5 1234.5 1234.5 1234,5
1234567.89 1234567.89 1234567.89 1234567,89

规律是：小数分隔符跟随 ​​Language​​ （​​de-DE​​ 是逗号），但千位分隔符一律不加。 所以 1234567.89 显示成 1234567.89，而不是 1,234,567.89。默认转换用的是「通用格式」，不带分组。

想显示成带千位分隔的样子，得自己写 StringFormat 或转换器。

第二，​​DateTime​​ 的格式也跟随 ​​Language​​ 。 同一个日期，Language=zh-CN 时显示成 2026/10/20 下午1:45:00，Language=en-US 时显示成 10/20/2026 1:45:00 PM。连「下午」「AM/PM」这种文字都会跟着变。

如果不给元素设 ​​Language​​ 会怎样？ 实测结果是继承到一个默认值 en-us，所以显示格式跟 en-US 一样。这就是为什么很多人的中文程序里，日期显示成了 10/20/2026 这种美式格式——不是程序写错了，是没人告诉它该用哪个区域。

想让它按中文显示，最简单的办法是在窗口上设一次：

这个设置会往下继承给所有子元素，所以设一次就够了。这件事下一篇讲格式化时还会再提到。

第三，转换器拿到的 ​​CultureInfo​​ 也跟随 ​​Language​​ 。 实测：元素 Language=de-DE 时，转换器的 culture 参数就是 de-DE；元素不设 Language 时是 en-US；如果显式写了 ConverterCulture，以它为准。这给了你一个控制转换器区域的开关。

第三，布尔值显示成 ​​True​​ / ​​False​​ 。 这是英文，界面上通常想显示成「是」「否」，那就需要转换器。

第四，​​null​​ 显示成空白。 空白和「值是空字符串」在界面上看不出区别，这正是第 4 章要用兜底值的原因。

第五，自定义类型只要有 ​​TypeConverter​​ 就能参与转换。 没有 TypeConverter 时，会退回到 ToString()，所以你的自定义类型最好重写 ToString()。

第六，来源 → 目标方向转换失败时，目标会回到「默认值」，而不是保持上一次的值。 这一条容易想错，单独验证过：把一个 GridLength 目标先喂 2*，再喂 abc，目标回到 *（也就是它的默认值）；char 目标先喂 X，再喂 YZ（两个字符转不过去），目标回到空格，也就是 char 的默认值。

第七，这种情况配 ​​FallbackValue​​ 是有效的。 实测：double 目标先喂 3.14 显示 3.14，再喂 abc 就变成 0；而同一个绑定配上 FallbackValue=-1 之后，喂 abc 就显示 -1。

这一条和第 4 章要讲的「兜底值」正好接上：默认转换失败属于「取不到值」，所以 ​​FallbackValue​​ 管得着。 但要注意区分——如果是转换器内部抛异常，那就不是「取不到值」，FallbackValue 救不了，这一点第 4 章会实测给你看。

还有一处方向上的区别要记牢：上面说的是来源 → 目标方向。下一节要讲的目标 → 来源方向失败时，行为完全不同：来源会保持原值。

1.3 文字 → 强类型来源：能解析才写回

反方向更有意思：界面上是字符串，来源是强类型，能不能写回去？

实测结果（在文本框里输入，看来源值变不变）：

目标类型 输入 来源值 结论
double 9876.5 9876.5 转成功
double abc 保持 9876.5 转失败，不写回
double 42（带空格） 42 首尾空格会被忽略
double 1e3 1000 支持科学计数法
int 3.7 保持原值 不四舍五入，直接拒绝
int 7 7 转成功
decimal 19.999 19.999 转成功
bool true / True True 两种大小写都认
bool 1 保持原值 1 不是合法布尔文字

图 3：能解析就写回，解析不了就保持上一次的合法值。

这里最重要的一条规律：转不过去时不会报错，也不会写回，来源保持原值。 界面上看起来就是「我输了但右边没变」。

这条规律决定了两个实用结论：

  1. 默认转换能省事，但也悄悄吞掉错误。用户输入了非法内容，界面不会有任何提示。要提示，就得配校验（第 6 章）。
  2. 想让「转不过去」这件事变得可见，要么加校验规则，要么在转换器里自己处理。

几个实用提醒：

枚举按名字更安全。 写 Middle 比写 2 可读性好得多，而且以后枚举顺序调整了也不会出错。

​char​​ 只能装一个字符。 输入两个字符会失败，这是很多人第一次做「首字母」输入框时踩的坑。

​GridLength​​ 的 ​ ​*​​ 、​​2*​​ 、​​Auto​​ 都能转。 我第一次测的时候被默认值骗了——GridLength 的默认值恰好就是 *，所以看起来像「转换失败但恰好相同」。后来改成先喂 2* 再喂 *，才看清 * 是能正常转过去的。这也提醒一件事：测试默认转换时，要先把目标改成别的值，否则「失败后回到默认值」和「转换成功」看起来一模一样。

​Visibility​​ 这种枚举，界面上一般用复选框配转换器，不直接输入文字。

自定义类型要给 ​​TypeConverter​​ 实现 ​​ConvertTo​​ ，否则反向（值 → 文字）只能走 ​​ToString()​​ 。 实测里，如果 CanConvertTo 返回 false，那么显示时就退回到 ToString()；如果返回 true，就会走你自己的转换逻辑。

有了上面的对照表，判断标准就很清楚了：

可以省略转换器的场合：

2.2 参数不合法时的两种处理

参数是手写的，写错很正常。转换器里应该有两种处理方式，选哪种看场景：

方式一：退回默认行为。 参数不对就用默认值，界面照常工作。

方式二：返回 ​​Binding.DoNothing​​ 。 参数不对就什么都不改，界面保持原样。

这两种都比「直接抛异常」好。抛异常会让整个界面崩掉，而参数写错只是个小问题。

因为判断用的是 OrdinalIgnoreCase，所以 Brush、brush、BRUSH 都能认。这一点在写代码时要注意，如果你想严格区分大小写，就换成 Ordinal。

2.4 参数里带特殊字符怎么办

参数里如果带 #、|、,、= 这类字符，建议用单引号把整串包起来：

为什么要这样写？因为 ConverterParameter 在 XAML 里是按字符串解析的，遇到某些字符时，解析器可能把它当成标记扩展或别的东西。单引号的作用是明确告诉解析器：这里面全是普通文字，别做额外解释。

实测里，写了单引号的参数传进转换器后，内容就是 '#174EA6|#B03A3A'，连单引号本身也一起传进去了。所以转换器里解析时要先把引号去掉：

3. 基于 Converter 的性别绑定案例

3.1 问题：一个性别字段，两个单选按钮

数据里 Gender 是一个字符串，值是「男」或「女」。界面上要的是两个单选按钮。

直觉写法是「男按钮绑一个布尔属性，女按钮绑另一个布尔属性」，但数据里根本没有这两个布尔属性。硬加的话，模型会被界面需求污染：本来一个字段能表达的信息，变成了三个字段还要手动保持同步。

3.2 Convert 方向：比较是否相等

逻辑很短，但要做两件事：确认 value 和 parameter 都是字符串，然后比较。任何一步不成立就返回 false，按钮不选中。

注意用的是 StringComparison.Ordinal，因为性别值是固定的两个字，不需要考虑区域差异。如果这里用忽略大小写的比较，反而可能把不该相等的值判成相等。

3.3 ConvertBack 方向：只在勾选时写回

这是本节最需要理解的一段：

为什么取消勾选不能返回一个值？ 想想用户点「女」的瞬间发生了什么：

  1. 女按钮 IsChecked 变成 true → 它的 ConvertBack 返回「女」→ 来源变成「女」。
  2. 同时，男按钮 IsChecked 变成 false → 它的 ConvertBack 被调用。

第 2 步如果返回了「男」，来源就被改回「男」了，跟第 1 步打架。返回 DoNothing 的意思是「这次我不参与」，来源就保持第 1 步写进去的「女」。

实测结果验证了这一点：

操作 Gender 男按钮 女按钮
初始 男 True False
点「女」 女 False True
代码改回「男」 男 True False
取消勾选「男」 男（没变） False False

最后一行是关键：取消勾选后，来源仍然是「男」 ，没有被改成「女」。DoNothing 起作用了。

图 6：两个按钮绑同一个来源，靠参数分工，靠 DoNothing 避免互相打架。

3.4 只用于显示的转换器要写 ConvertBack 吗

GenderToTextConverter 只把「男」变成「男员工」，从界面不会反向写回。这种情况下 ConvertBack 直接拒绝：

不要写成 ​​return null​​ 或者 ​​return value​​ 。 那样会把「反向不可用」这件事变得含糊，将来别人误用了双向绑定，错误会很难查。直接抛 NotSupportedException，问题会立刻暴露出来。

4. FallbackValue 与 TargetNullValue 属性

本节目标

  • 分清这两个属性各自负责什么情况。
  • 知道它们同时写的时候谁优先。
  • 学会用它们让界面不再出现「莫名其妙的空白」。

4.1 两种「没值」，两种兜底

界面出现空白时，背后可能是两种完全不同的原因：

情况 含义 该用哪个兜底
来源属性取到了，但值是 null 数据确实存在，只是内容为空 TargetNullValue
来源属性根本取不到 路径写错了、转换失败了 FallbackValue

这两个属性的分工就是按这个划分的。名字也说明了含义：TargetNullValue 管「送到目标的值是 null」，FallbackValue 管「拿不到值，退一步用什么」。

图 7：来源为 null 走 TargetNullValue；取不到值走 FallbackValue。

4.2 实测：单独写各自的区别

先准备一个值为 null 的来源属性，然后试三种写法：

写法 显示结果
什么都不写 空白
只写 FallbackValue="兜底文字" 空白
只写 TargetNullValue="空值提示" 空值提示

这个结果值得停下来看一会儿。来源是 ​​null​​ 时，​​FallbackValue​​ 不生效。 因为绑定确实取到了值（值就是 null），这不算「取不到」，所以走的是 TargetNullValue 那条路。

只有下面这种情况才会走 FallbackValue：

写法 显示结果
路径不存在，不写兜底 空白
路径不存在 + FallbackValue="路径不存在" 路径不存在

路径不对时，绑定根本取不到值，这时 FallbackValue 才上场。

4.3 两者都写的时候谁优先

实测结果：来源是 null 时显示 「空值提示」 。也就是说，TargetNullValue 优先。

这个顺序是合理的：TargetNullValue 描述的是更具体的情况（值存在且为 null），应该比笼统的 FallbackValue 优先。

把来源从 null 改成「有值了」，显示跟着变成「有值了」；再改回 null，又变回「空值提示」。整个过程是活的。

4.4 转换器返回 null 时会怎样

这里有个容易踩的点。转换器可以返回三种「特殊」结果：

转换器返回 绑定的反应
Binding.DoNothing 跳过这次更新，目标保持原值
null 把空值送到目标；配了 TargetNullValue 就换成它
DependencyProperty.UnsetValue 视作「没有值」，走 FallbackValue

实测确认：

场景 目标值
转换器返回 null，不写 TargetNullValue 空白
转换器返回 null + TargetNullValue="空值提示" 空值提示
转换器返回 DoNothing（目标原本有值） 保持原值
转换器返回 UnsetValue 走 FallbackValue

所以如果你写了一个「可能返回空」的转换器，记得同时配上 TargetNullValue，否则界面上会出现空白，而且分不清是数据问题还是转换问题。

4.5 转换器抛异常时，兜底还能用吗

实测结果：

​FallbackValue​​ 救不了抛异常的转换器。 异常会直接冒到触发绑定的那行代码上，这一次转换没有产出任何值，目标保持默认值（对 TextBlock.Text 来说就是空字符串）。

这个结论很重要，它说明两件事：

  1. FallbackValue 处理的是「正常流程里取不到值」，不是「代码崩了」。
  2. 想让转换失败时界面好看，转换器内部要自己 try/catch，返回 DoNothing 或 null，而不是让异常跑出去。

ColorNameToBrushConverter 就是这么写的——颜色名不合法时自己接住异常，返回 DoNothing。

本节目标

5.1 三类异常，三种去处

绑定过程中可能出错的地方有三处，处理方式各不相同：

出错位置 会发生什么
转换器内部 异常直接冒到触发绑定的代码，这一次转换没有结果
来源属性的 setter 异常会冒出来，但绑定的值可能已经部分更新
来源属性的 getter 异常同样会冒出来，绑定这一次拿不到值

6. 自定义 ValidationRule

本节目标

  • 知道校验规则在绑定的哪一步介入。
  • 知道默认校验步骤拿到的是什么类型，以及为什么经常拿到字符串。
  • 学会写带参数的规则，并复用到多个字段。
  • 理解 ValidationResult 的第二个参数是干什么用的。

6.1 校验规则插在哪个位置

绑定的写回方向有四个步骤，校验规则可以插在其中三个位置上：

ValidationStep 规则拿到什么 什么时候用
RawProposedValue 用户敲进去的原始值（通常是字符串） 想校验「用户输入了什么」
ConvertedProposedValue 已经过类型转换的值 想校验「转换后的值对不对」
UpdatedValue 来源属性被更新之后的值 想校验「最终存进去的值」

默认是 RawProposedValue。这一点很关键，因为很多人以为规则里拿到的是转换后的数字，其实是字符串。

实测结果：

三行结果说明：

  • 默认步骤拿到的是 String，所以要自己 int.TryParse。
  • 改成 ConvertedProposedValue，拿到的才是 Int32。
  • UpdatedValue 拿到的居然是 BindingExpression 对象，不是值本身。因为这一步已经更新完了，规则只能通过表达式去读值。这个步骤很少用，除非要做「多个字段联合校验」。

6.6 ValidationResult 的第二个参数是替换值

ValidationResult 的构造函数是 ValidationResult(bool isValid, object errorContent)。第二个参数在文档里叫「错误内容」，但它还有一个不太为人知的作用：当它是非字符串内容时，会被当作替换值继续往下走。

实测结果：

规则返回 输入 来源值 错误数 提示内容
new(false, 0) 42 4 1 0
new(false, 99) 42 4 1 99
new(true, 10) 42 42 0 无
new(false, "不是偶数") 7 保持 1 不是偶数

这里要仔细看。前两行返回的是数字，来源值变成了 4（初始值），提示内容是那个数字；第三行返回 true，校验通过，来源值保持 42，没有替换。

所以结论是：

  • 返回 false 时，校验失败，来源不会被更新，那个非字符串内容会显示成错误提示。

  • 返回 true 时，校验通过，值正常写回，第二个参数基本不起作用。

    「替换值」这个说法在 WPF 里其实是个容易误导人的说法。 实测表明，校验失败时来源保持原值，不会真的被替换掉。真正想做「超范围就改成上限」，正确做法是返回 ​​true​​ 并在转换器或强置回调里处理，或者干脆在来源属性的 setter 里做修正。

这一点跟很多网上文章的说法不一样，所以特别提醒：以实测为准。

6.8 规则里抛异常会怎样

实测结果：

异常直接冒出来，跟转换器抛异常一样。所以规则里也要自己接住可预期的异常，返回 new ValidationResult(false, "提示")，而不是让异常跑出去。

6.9 还有三种校验方式

除了自定义 ValidationRule，WPF 还提供了三种现成的校验，都通过绑定上的开关启用：

开关 作用 来源需要实现
ValidatesOnExceptions 捕获来源 setter 抛的异常，转成校验错误 无
ValidatesOnDataErrors 读取 IDataErrorInfo 提供的错误 IDataErrorInfo
ValidatesOnNotifyDataErrors 读取 INotifyDataErrorInfo 提供的错误 INotifyDataErrorInfo

实测结果：

这三条路各有适用场景：

​ValidatesOnExceptions​ 适合来源 setter 里本来就有范围检查的情况。它把「抛异常」这件事变成了「校验错误」，比默默忽略好得多。代价是异常本身有性能开销。

​ValidatesOnDataErrors​ 是老式做法，来源实现 IDataErrorInfo，里面有个索引器 this[string columnName] 返回错误信息。写法简单，缺点是不能异步、不能一个属性报多条错。

​ValidatesOnNotifyDataErrors​ 是新式做法，来源实现 INotifyDataErrorInfo，支持多条错误、支持异步校验。写新代码优先用它。

顺便注意一个细节：实测里「不写 ValidatesOnNotifyDataErrors，输入 10」也报出了 1 个错误。因为来源实现了 INotifyDataErrorInfo，而这个开关在新版本里默认是开的。所以实现了这个接口就要小心，错误会自动冒出来。

6.10 跟做：搭出第 6 章页签

6.11 跟做检查点

  1. 初始状态三个文本框都没有红框（因为校验只在写回时触发）。
  2. 在「只能填偶数」里输入 7，出现红框，鼠标悬停能看到「7 不是偶数」。
  3. 改成 8，红框消失。
  4. 输入 abc，红框出现，提示「「abc」不是整数」。
  5. 在年龄框里输入 70，红框出现，提示「不能大于 60 岁」。

  7. 把 ValidationStep 改成 ConvertedProposedValue，确认规则里拿到的变成 Int32（可以加一行调试输出验证）。
  8. 加两条规则，确认第一条失败时第二条不会被调用。

  1. 写一个规则，检查手机号是 11 位数字。用 Regex 实现，失败时提示「手机号格式不对」。
  2. 给「只能填偶数」那个文本框写一个样式，让红框和提示文字同时显示（用 ControlTemplate + AdornedElementPlaceholder）。

四道处理速查表

把这一篇的核心结论收在一起：

处理 谁来做 关键点
默认转换 WPF 内置 六种办法按顺序试；数字用不变文化，日期用元素 Language；转不过去就保持原值
自定义转换 IValueConverter 参数永远是字符串；失败时返回 DoNothing 而不是抛异常
兜底值 FallbackValue / TargetNullValue 来源为 null 走 TargetNullValue；取不到值走 FallbackValue；救不了异常
校验 ValidationRule 默认步骤拿到字符串；规则按顺序执行，失败即停；失败时来源不更新

现象 原因 解决

结语

这一篇的六个知识点，其实在回答同一件事的两面：

一面是「值怎么变成界面能显示的样子」 ——默认转换兜住了大部分常规类型，转换器负责剩下的翻译工作，参数让一个转换器能顶好几个用。

另一面是「值不对劲时怎么办」 ——兜底值让空白变得有含义，异常处理让程序不崩，校验规则让用户知道哪里填错了。

写完这一篇，你应该能做到两件事：

  1. 拿到一个数据类型和界面控件不匹配的需求，能立刻判断「这是默认转换能做的，还是要写转换器」。
  2. 写转换器时，知道参数是什么类型、失败时该返回什么、异常该怎么处理。

再往深处走，会碰到异步校验、INotifyDataErrorInfo 的完整实现、MultiBinding 与 IMultiValueConverter、以及基于 CollectionViewSource 的过滤排序。这些都在这一篇的基础上展开，底子稳了，学起来会快很多。

动手顺序建议：先把第 1 章的默认转换对照表跑一遍，知道边界在哪；再写第 3 章的性别绑定，这是最典型的转换器用例；最后练第 6 章的校验规则，把「失败时给用户看得见的反馈」这件事做完整。

祝学习顺利。
