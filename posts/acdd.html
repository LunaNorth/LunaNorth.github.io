2. Lambda

Lambda 的样子是“参数 => 表达式”。左边的 error、_ 或空括号是参数，右边是要执行的内容。

1. 本节目标

做完后应该看到：在文本框里把“小明”改成“小红”，下面的文字也跟着变成“小红”。

2. 一句话原理

[ObservableProperty] 是源生成器特性。你在字段上贴标签，编译器在后台帮你生成一个带 get、set 和 PropertyChanged 通知的公开属性。

本章真正要学的思维：状态变化要能被界面看见。

  • 字段是类内部的存储，属性是外部观察这个状态的窗口。
  • 属性变化后发出 PropertyChanged，WPF 才知道要重新读取绑定值。
  • [ObservableProperty] 只是帮你少写重复代码，它没有改变“状态变化 → 通知 → 界面刷新”这条链路。
  • 判断方法：这个值在运行中会变吗？会变，就需要通知；只是固定常量，就不需要。
  • 不要把所有东西都做成可通知属性。先分清“状态”和“常量”，再决定用哪种写法。

7. 关键代码逐段看

先看 [ObservableProperty]。

它不是普通的 C# 注释，而是告诉源生成器：“请把这个字段变成可通知属性。”

再看 private string _name = "小明";。

你写的是私有字段，生成出来的是公开属性 Name。所以 XAML 绑定的是 Name，不是 _name。

最后看 public partial class。

这里要重点理解“为什么必须写 partial”。

partial 的意思是“这个类可以分成几部分来写”。平时一个类写在一个文件里；加了 partial 后，编译器允许你在另一个文件里再写一次同名类，最后把它们合并成一个类。

[ObservableProperty] 的工作过程可以想成：

  1. 你在 ObservableDemoViewModel.cs 里写“左半边”：字段 _name 和特性 [ObservableProperty]。
  2. 编译时，源生成器自动生成“右半边”：公开属性 Name、get/set 和属性变化通知。
  3. 编译器把“左半边”和“右半边”拼成一个完整的 ObservableDemoViewModel。

简化示意如下（不是生成器逐字输出的代码）：

如果类不写 partial，编译器就不允许把生成器补出来的 Name 属性并进这个类，源生成器也就无法完成工作。所以你看到的不是“框架要求你多写一个单词”，而是“这个类要和自动生成的代码拼在一起，必须先允许拆分”。

可以用一个生活化的比喻：partial 就像告诉编译器“这个类可以由两个人分别写两半，最后装订成一本完整的书”。[ObservableProperty] 负责写另一半，你负责写字段这一半；没有 partial，编译器就不允许“装订”。

还要注意：partial 只影响编译时怎么组织代码，不会多创建一个对象，也不会改变运行结果。它不是继承，也不是接口。

以后遇到类似“特性 + 源生成器”的写法，可以固定问自己三个问题：

  1. 这个特性会不会在编译时生成代码？
  2. 生成的代码要放到哪个类里？
  3. 那个类有没有用 partial 给生成器留位置？

想清楚这三点，就不容易漏写 partial 了。

2. 一句话原理

按钮不直接调用方法，而是绑定一个命令；命令再调用 ViewModel 方法。ViewModel 不自己创建服务，而是让 IoC 容器把服务从构造函数送进来。

本章真正要学的思维：依赖不要自己造，先声明出来，再集中装配。

  • 命令思维：界面不直接调用方法，而是发出“我要执行这个动作”的意图；ViewModel 决定具体做什么。
  • IoC 思维：构造函数是“需求清单”，注册是“提供能力”，解析是“取装配好的成品”。
  • 判断方法：这个类需要什么？它应该依赖接口还是具体实现？谁负责创建它？
  • 迁移到其他项目：先找“对象在哪里组装”，通常就是启动入口或 App 类；找到组装点，就能看懂整个依赖关系。
  • 不要背 AddSingleton 的顺序，先画依赖箭头：谁需要谁，谁在最上层，谁在底层。

4. CommunityToolkit中的通知属性特性使用

1. 本节目标

用 [NotifyPropertyChangedFor] 解决“一个字段变化，另一个计算属性也要刷新”的问题。

做完后在两个文本框里改姓或名，下面的完整姓名会立即更新。

2. 一句话原理

[ObservableProperty] 只通知自己生成的属性；如果另一个属性依赖它，就要额外告诉通知系统：“这个属性变了，也请通知另一个属性。”

本章真正要学的思维：状态之间会互相影响，变化要沿着依赖关系传播。

  • FirstName 和 LastName 是原始状态，FullName 是由它们算出来的结果。
  • [ObservableProperty] 只负责通知自己；[NotifyPropertyChangedFor(nameof(FullName))] 负责告诉界面：“依赖它的 FullName 也变了。”
  • 判断方法：改一个值以后，界面上还有哪些显示会受影响？把这些依赖列出来，再决定通知谁。
  • 能算出来的值，尽量不要重复存成字段。重复存两份状态，就多一份“忘记同步”的风险。
  • 迁移到其他场景：总价、库存、全名、格式化地址、状态文字，都是“原始状态 + 计算属性”的组合。

5. CommunityToolkit中的命令与验证特性使用

1. 本节目标

让 ObservableValidator 检查输入，并让命令根据验证结果自动禁用或启用按钮。

做完后：

  • 姓名合法时，“提交”按钮可用。
  • 姓名清空或少于两个字符时，按钮变灰，并显示错误文字。

2. 一句话原理

验证特性负责判断输入是否合法，HasErrors 保存结果；命令的 CanExecute 读取这个结果，决定按钮能不能点。

本章真正要学的思维：规则先判断，状态再记录，界面最后根据状态变化。

  • 输入值先经过验证规则，得到“合法 / 不合法”的结果。
  • HasErrors 保存这个结果，错误文字告诉用户哪里不对。
  • CanExecute 读取验证状态，决定按钮是否可用。
  • 判断方法：什么算合法？错误信息给谁看？这个动作在什么条件下才能执行？
  • 迁移到其他场景：登录、保存设置、提交订单、导入文件，都是“规则 → 状态 → 按钮”的同一套逻辑。
  • 不要把验证写散在按钮点击事件里。规则集中在 ViewModel，界面只负责显示结果。

1. 本节目标

用 [RelayCommand] 生成异步命令，让按钮启动一个耗时任务；任务完成后通过 WeakReferenceMessenger 发送消息，再由实现了 IRecipient<T> 的 ViewModel 接收。

做完后点击“开始异步加载”，会先看到“正在加载…”，约一秒后变成“加载完成”，并显示：

2. 一句话原理

异步命令负责“开始做一件耗时的事”，消息负责“做完后通知关心它的人”。按钮不需要一直等待，接收方也不需要认识发送方。

本章真正要学的思维：耗时任务要管理过程，完成通知要解耦。

  • 异步命令不只管“开始”，还要管“正在执行”“执行完成”“执行失败”这些过程状态。
  • 界面要根据 IsRunning 等状态决定按钮是否可用、是否显示“正在加载…”。
  • Messenger 是发布/订阅：发送方只负责发消息，不需要知道谁在听；接收方只关心自己感兴趣的消息。
  • 判断方法：这个任务要多久？执行期间界面要不要禁用？完成后谁需要知道？失败了怎么显示？
  • 迁移到其他场景：文件导入、HTTP 请求、后台计算、批量处理，都可以沿用“异步命令 + 状态 + 消息”的组合。
  • 不要让页面之间互相直接引用。能通过消息解耦的地方，就不要硬连在一起。
