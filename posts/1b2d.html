IoC瞬态与依赖注入进阶入门学习笔记

80672026-11-172026-11-1734 分钟

这份笔记按你给的 4 个目录重写，重点不是再解释一遍“什么是接口”，而是把四件事分开看清楚：

  1. 什么时候复用对象，什么时候重新创建对象。
  2. 构造函数一层套一层时，容器怎样递归创建。
  3. 对象已经创建后，怎样通过属性补依赖。
  4. 同一个接口有多个实现时，怎样按名字选择。

这份笔记继续使用控制台，不是因为它更“高级”，而是因为它能把对象创建过程直接打印出来。等你看懂输出，再放回 WPF 时，只是把 Program.Main 换成 App.OnStartup，把 Console.WriteLine 换成 TextBlock 的绑定。

四章主线

章节 本章只解决一个问题 做完会看到
1. IOC瞬态模式与单例模式逻辑整合 缓存到底影响了谁 两次请求是否拿到同一个对象
2. 无限层级的依赖注入逻辑处理 构造函数参数怎样递归解析 Level1 -> Level2 -> Level3
3. 属性注入逻辑处理 对象创建后怎样补属性 手动注入和容器注入的结果
4. 单接口多实现注入逻辑处理 同一个接口怎样选实现 Email 和 Sms 两个结果

先把三个词说透

词 不要这样理解 应该这样理解
注册 注册时马上创建对象 只写“要这个接口时，用哪个创建方法”
解析 解析一定创建新对象 先看缓存，再决定创建还是复用
生命周期 一个类型永远只有一种模式 每次请求可以选择是否使用缓存

SimpleIoc 的 GetInstance<T>() 默认会查缓存；GetInstanceWithoutCaching<T>() 表示“这次请求不使用缓存”。这不是在注册时给类型永久贴一个“瞬态”标签，而是你在每次请求时做的选择。

1. IOC瞬态模式与单例模式逻辑整合

1. 本节目标

分清两件事：

  1. GetInstance<T>() 默认会复用已经缓存的对象。
  2. GetInstanceWithoutCaching<T>() 只让“这次请求的目标对象”不使用缓存，不会自动把它内部的依赖也全部换成新的。

做完后你会看到四行 True：

2. 一句话原理

注册只是写下“怎么造”，缓存才决定“这次要不要复用”。GetInstance 像先看保温壶里有没有；GetInstanceWithoutCaching 像这次不查保温壶，重新做一杯。

这不是 bug，而是生命周期要“逐类型看”的结果。以后你看到“外层是新的，内层却是旧的”，先问自己：我改变的是哪一层的获取方式？

你只请求 Level1ViewModel，容器会自己把后面的 Level2 和 Level3 补上。做完后看到：

这里的“无限层级”不是“无限循环”。它的意思是：只要构造函数参数还有依赖，容器就继续往下解析；如果依赖形成环，就必须停下来报错。

2. 一句话原理

容器看到构造函数需要参数，就去找这个参数类型的登记；如果那个类型也有构造函数参数，就继续往下找，直到最底层没有参数为止。这像装配线：先装最里面的零件，再一层层往外装。

容器不是只写死了三层。它的思路是：看构造函数有哪些参数，对每个参数调用解析；如果参数自己还有构造函数参数，就继续递归。你把三层换成五层，只要每层都注册好，请求代码仍然只写 GetInstance<Level1ViewModel>()。

那“无限”什么时候应该停？两种情况必须停：

  1. 参数类型没有注册：应该抛出“未注册”异常，而不是悄悄塞 null。
  2. 依赖形成环：例如 A 依赖 B，B 又依赖 A，必须检测并报错，不能无限递归。

本笔记的自定义容器 MiniContainer 已经在内部用 _creating 集合做循环检查；附录会看到完整写法。SimpleIoc 的循环依赖处理以你实际版本为准，初学阶段不要让类之间互相依赖。

为什么先讲手动注入，再讲自动注入？因为手动版本能让你看清顺序：

  1. 先有对象。
  2. 再拿到依赖。
  3. 再把依赖赋给属性。

自动版本只是把第 2、3 步交给容器循环处理。你先懂顺序，再看反射代码就不会觉得它是凭空出现的。

属性注入适合“可选依赖”或“稍后补充”的场景。如果对象离开某个依赖就无法工作，优先用构造函数注入，因为依赖关系更清楚，也不容易出现“忘记给属性赋值”的半成品对象。

7. 关键代码逐段看

代码 意思
() => new EmailMessageService() 工厂：容器真正需要时才创建
"Email" 这个实现的 key，也就是标签
Register<IMessageService>(factory, key) 同一个接口可以登记多个带 key 的实现
GetInstance<IMessageService>("Email") 按 key 选择具体实现
GetInstance<IMessageService>("Sms") 换一个 key，拿到另一个实现

为什么这里用工厂，而不是直接写两个 Register<IMessageService, ...>？因为两个实现对应同一个接口，如果只按类型注册，后一次可能覆盖前一次，你也无法清楚表达“我要哪一个”。key 让“接口类型”和“具体实现”之间多了一层选择。

你也可以把它想成菜单：IMessageService 是“饮料”这个类别，"Email" 和 "Sms" 是两个菜名。你说菜名，厨房才知道做哪一道。

  • 没有忘记 ioc.Reset()。
  • 输出分别是 Email 和 Sms。

11. 常见错误

现象 原因 解决
两个结果一样 两次注册用了同一个 key 改成不同的 key
报“未找到 key” 获取时字符串拼错 逐字对照注册和获取
报“未注册” 只写了实现类，没有注册接口 用 Register<IMessageService>(..., key)
想改一个实现却改到另一个 两个类名很像 先看类名，再看 key，再看返回值
工厂里直接 new 了错误类型 复制后忘记改类名 检查 () => new ... 里的类

13. 小结与迁移

这一章要记住：

单接口多实现时，接口负责统一用法，key 负责选择具体实现。

放回 WPF 时，同一个“通知服务”可能对应邮件、短信、站内信。页面只依赖 INotificationService，具体用哪个实现由组合根或配置决定。不要把选择逻辑散落到每个按钮事件里。
