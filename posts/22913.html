1.3 Loaded：元素树已经可用

在窗口构造函数中订阅：

Loaded 适合做：

  • 读取控件当前的 ActualWidth、ActualHeight。
  • 第一次加载数据。
  • 根据界面尺寸调整内部布局。

但 Loaded 不保证窗口已经完成第一次绘制。此时界面可能已经参与布局，却还没有真正显示到屏幕上。

1.4 ContentRendered：第一次渲染完成

ContentRendered 比 Loaded 更晚，通常适合：

  • 启动首次进入动画。
  • 在界面已经可见后显示引导层。
  • 需要等待第一次画面呈现再执行的操作。

不要把两者简单记成「Loaded 是加载，ContentRendered 是渲染」就结束。真正的判断方法是：你需要元素树可用，还是需要第一帧已经画出来？

1.5 Closing 与 Closed：一个能取消，一个不能取消

两者最重要的区别：

事件 时机 能否取消 常见用途
Closing 关闭动作正在进行 可以，设置 e.Cancel = true 询问是否保存、阻止误关闭
Closed 窗口已经关闭 不可以 释放资源、记录最终状态

如果用户在 Closing 中取消关闭，后续的 Closed 和 Application.Exit 都不应继续执行。

1.6 Exit：应用退出时收尾

Exit 是应用级事件，不等于某一个窗口的 Closed。如果应用有多个窗口，或者 ShutdownMode 不是 OnMainWindowClose，窗口关闭和应用退出之间可能没有你想象的同步关系。

1.7 三种全局异常入口

图 3：三个入口覆盖不同来源，不能只写一个就以为捕获了全部异常。

在 App 构造函数中注册三个入口：

入口一：DispatcherUnhandledException

它负责 UI 线程上的未处理异常，例如按钮点击、布局、渲染和 Dispatcher.BeginInvoke 回调中的异常。设置 e.Handled = true 可以让程序继续运行，但这不代表异常已经修复。

生产程序中至少应记录完整堆栈，并提示用户保存工作。对于无法安全恢复的异常，继续运行反而更危险。

入口二：AppDomain.UnhandledException

它能看到非 UI 线程中最终没有被处理的异常。这个入口主要用于记录和诊断，通常不能像 DispatcherUnhandledException 那样简单地让进程继续运行。

入口三：TaskScheduler.UnobservedTaskException

它处理「任务已经失败，但异常一直没有被 await、Wait() 或其他方式观察」的情况。触发时间可能比任务真正失败晚，不能把它当成实时错误通知。

2. 对象事件总结说明

本节目标

  • 把 WPF 中常见事件分成应用生命周期事件、普通对象事件和路由事件三层。
  • 理解事件发布者和订阅者的关系。
  • 分清 Click、PreviewMouseDown、MouseDown 各自处于什么阶段。
  • 知道什么时候该用 sender，什么时候该看 e.OriginalSource。

2.1 三层事件模型

图 4：同一段交互里，三层事件可能同时出现。先判断它属于哪一层，再判断传播方式。

第一层：应用生命周期事件

例如 Application.Startup、Application.Exit、Window.Loaded、Window.Closing。它们描述的是程序或窗口的生命周期，通常只发生一次，或者发生次数很少。

第二层：对象普通事件

例如属性变化通知 PropertyChanged、按钮的 Click、定时器的 Tick。普通事件由对象自己触发，通常没有沿元素树自动传播的过程。

第三层：路由事件

例如 PreviewMouseDown、MouseDown、KeyDown。路由事件会沿元素树按特定策略传播，可能先向下，再向上。

判断一个事件时先问三个问题：

2.2 事件处理器里的两个 sender

在 WPF 中经常会看到：

它们不是一回事：

名称 含义 典型用途
sender 当前挂载这个事件处理器的对象 知道是哪个控件注册了处理器
e.Source 路由事件开始时设置的逻辑来源 逻辑树上的来源
e.OriginalSource 最初命中的可视元素 判断鼠标真正点到了什么

例如窗口订阅了 MouseDown，用户点在窗口里的一个 TextBlock 上：

  • sender 可能是窗口。
  • e.OriginalSource 可能是那个 TextBlock。
  • e.Source 可能经过逻辑树调整，和 OriginalSource 不一定相同。

不要用 sender 去判断「用户点了哪个子元素」。这类判断通常应该看 e.OriginalSource。

2.3 Click 不是 MouseDown 的别名

按钮的 Click 表示一次完整的点击语义：鼠标在按钮上按下，又在同一个按钮上抬起，并且没有被取消。MouseDown 只表示按下的瞬间。

所以不能这样理解：

如果按下后把鼠标拖出按钮再抬起，MouseDown 已经发生，但 Click 可能不会发生。

  • 在 Loaded 里订阅同一个事件多次，刷新页面后处理器执行多次。

4.2 鼠标捕获为什么必要

拖动速度很快时，鼠标可能瞬间移出卡片。如果没有捕获，卡片收不到后续的 MouseMove 和 MouseUp，拖动就会卡住。

捕获的意思是：在这段时间内，鼠标输入优先送到捕获它的元素。即使指针已经离开卡片边界，卡片仍然能收到移动和抬起。

6. 路由事件的处理过程

本节目标

  • 理解路由事件为什么需要「路由」。
  • 能画出 PreviewMouseDown 的隧道路径和 MouseDown 的冒泡路径。
  • 理解 sender、e.Source、e.OriginalSource 在路由中的不同角色。
  • 知道 e.Handled 对后续处理器的影响。
  • 会使用 AddHandler(..., handledEventsToo: true) 观察已被处理的事件。

6.1 三种路由策略

WPF 路由事件常见三种策略：

策略 传播方向 典型事件
隧道 从根节点向目标向下 PreviewMouseDown
冒泡 从目标向祖先向上 MouseDown
直接 只作用于来源本身 MouseEnter、部分控件自定义事件

问题 检查点

处理器重复执行 是否重复订阅了同一个事件

综合练习

练习一：做一个可取消的关闭流程

要求：

  1. 在窗口中放一个 TextBox。
  2. 文本框有内容且未保存时，关闭窗口弹出确认。
  3. 用户选择取消时，窗口保持打开。
  4. 用户选择不保存时，记录 Window.Closing 和 Window.Closed。

提示：取消关闭只能在 Closing 中做，Closed 已经来不及。

练习二：做一个受限制的拖动卡片

要求：

  1. 卡片只能在画布内移动。
  2. 拖动时显示实时坐标。
  3. 按 Esc 取消本次拖动并回到原位。
  4. 双击卡片复位。

提示：按下时同时记录 _dragStart 和 _cardStart，取消时恢复 _cardStart。

练习三：做一个框选统计器

要求：

  1. 画布中有至少四个项目。
  2. 支持从四个方向框选。
  3. 显示选中数量和名称。
  4. 按住 Ctrl 时追加选择，不按 Ctrl 时重新选择。

提示：先把「本次框选结果」和「累计选择集合」分开，再处理 Ctrl 状态。

练习四：观察路由事件

要求：

  1. 做四层嵌套容器。
  2. 记录 Preview 和普通 MouseDown。
  3. 在中间层设置 Handled。
  4. 使用 handledEventsToo 增加一个旁路观察器。
  5. 比较两次日志的差异。

提示：不要只看事件名，记录 sender.Name 和 OriginalSource。

结语

这一篇的六个主题看起来分散，其实都在回答同一个问题：一个界面操作是怎样在正确的时间、沿着正确的对象关系，改变正确的状态。

生命周期告诉你什么时候可以开始和收尾；对象事件告诉你谁在通知谁；鼠标事件告诉你输入从哪里来；拖动和框选把输入变成几何状态；路由事件则解释这些通知为什么能穿过一层层容器。

学习时不要只复制最终代码。每做完一章，都回到运行结果问自己三个问题：

能回答这三个问题，再遇到新的 WPF 控件或交互需求时，就不会只靠背事件名了。
