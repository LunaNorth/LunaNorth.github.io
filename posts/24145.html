1. 路由事件的拦截

本节目标

完成本章后，你应当能够：

  • 说清 Preview 阶段和普通冒泡阶段拦截的区别。
  • 知道 e.Handled = true 到底影响了什么。
  • 用日志证明拦截后哪些处理器没有执行。
  • 理解 handledEventsToo 为什么能看到已处理事件。
  • 知道什么时候该拦截、什么时候不该拦截。

1.5 handledEventsToo：旁路观察

如果确实需要在已处理事件之后继续观察，可以注册：

handledEventsToo: true 适合：

  • 日志和诊断。
  • 全局快捷键监听。
  • 需要知道「事件确实被处理了」的监控。

不适合：

  • 绕过业务拦截，继续执行危险动作。
  • 在多个层重复做同一件事。
  • 用旁路观察代替清晰的业务设计。

2. 路由拦截后的逻辑执行

本节目标

  • 知道拦截处理器应当完成哪些收尾动作。
  • 会把「判断规则」和「界面处理」分开。
  • 能用 PreviewKeyDown 拦截快捷键。
  • 理解为什么拦截后还要给用户反馈。
  • 避免用 Handled 静默吞掉所有输入。

2.1 拦截后的四步

图 4：识别条件、记录证据、更新界面、阻止默认动作，四步缺一不可。

一个可维护的拦截处理器通常按顺序做四件事：

2.2 先判断，再拦截

错误做法：

这段代码把输入框中的所有按键都锁死了。正确做法是先判断：

这里只处理 Ctrl + A/C/V/X/Z，其他按键继续按正常流程处理。

2.3 为什么 Ctrl+C 要在 Preview 阶段处理

输入框自己会处理复制、粘贴、撤销等命令。如果等到普通 KeyDown，输入框可能已经先执行了默认行为。

在 Preview 阶段拦截，可以在默认命令执行前决定是否继续。

2.4 跟做：拦截后的三种动作

Ctrl+V 如果不在拦截规则里，就正常执行粘贴。不要把「拦截一个快捷键」写成「禁止整个输入框」。

2.5 运行截图

图 5：Ctrl+C 被拦截后，界面显示审计结果，日志中记录拦截和阻止默认复制。

2.6 跟做检查点

  1. 在输入框按 Ctrl+C，界面显示已拦截。
  2. 日志中至少有「识别快捷键」「记录审计」「阻止默认复制」三类信息。
  3. 按 Ctrl+V，如果没有被规则命中，应正常粘贴。
  4. 按普通字母，不应被拦截。
  5. 取消拦截逻辑后，Ctrl+C 应恢复输入框默认行为。

2.7 常见错误

现象 原因 修正
所有按键都没反应 无条件 e.Handled = true 只在规则命中时拦截
输入框的复制失效 拦截了 Ctrl+C，但没有替代行为 明确产品规则，提供替代动作
日志写了但用户不知道 只写后台日志 同步更新界面提示
拦截写在 KeyUp 默认动作已经执行 改到 PreviewKeyDown 或 PreviewTextInput
快捷键判断漏掉修饰键 只判断 e.Key 同时检查 Keyboard.Modifiers

2.8 小练习

  1. 只拦截 Ctrl+S，并显示“已保存”的模拟状态。
  2. 拦截 Ctrl+C 时把复制内容写入自己的日志，不调用系统剪贴板。
  3. 给拦截增加开关，关闭后恢复默认输入框行为。
  4. 把规则函数移到 InteractionRules，写一个不需要启动界面的测试。

3. 键盘输入事件

本节目标

  • 分清按键事件和文本输入事件。
  • 理解 PreviewKeyDown、KeyDown、TextInput、TextChanged 的先后关系。
  • 会用 Keyboard.Modifiers 判断 Ctrl、Shift、Alt。
  • 知道输入法组合输入为什么不能只靠 KeyDown 处理。
  • 能做一个可观察的键盘输入实验框。

3.1 键盘事件不是只有 KeyDown

图 6：先有按键，再有字符；文本控件最后还会报告文本已经变化。

常见顺序可以理解为：

但这不是每个按键都完全相同的固定流水线：

  • 方向键、F1、Esc 可能没有字符输入。
  • 输入法组合输入可能产生多个字符，KeyDown 与最终文字不一定一一对应。
  • 控件可能自己处理某些按键，导致普通事件不再执行。

  3. 做一个只允许输入数字的输入框，先思考应该拦截 KeyDown 还是处理 TextInput。

4. 拖拽事件

本节目标

  • 理解拖放为什么需要拖动源、数据对象和目标区域共同配合。

4.6 跟做检查点

  1. 鼠标在拖动源按下后轻微移动，不应启动拖放。
  2. 移动超过系统阈值，鼠标应进入拖放状态。
  3. 拖到目标区域，目标边框或状态应显示允许复制。
  4. 松开鼠标，目标显示接收到的文本。
  5. 拖到不支持的区域，效果应为 None。

5. Touch与多点触控事件

本节目标

  • 分清原始触摸事件和操作事件。
  • 会用 TouchDevice.Id 区分不同触点。
  • 会记录每个触点的位置。
  • 理解 ManipulationStarting、ManipulationDelta、ManipulationCompleted 的作用。
  • 没有触屏时也能通过模拟和规则测试学习多点触控。
  • 会计算双指距离和缩放比例。

5.1 Touch 与 Manipulation 是两层

操作事件

5.8 跟做检查点

  1. 在触屏上单指按下，触点数量变为 1。
  2. 第二根手指按下，触点数量变为 2。
  3. 两指拉开，缩放值增大；两指靠近，缩放值减小。
  4. 任意一根手指抬起，触点数量减少。

  6. 缩放值始终在 0.6 到 1.8 之间。

5.9 常见错误

现象 原因 修正
第二根手指覆盖第一根 只保存一个 Point 用触点 Id 做字典键
TouchUp 收不到 没有捕获触点 调用 CaptureTouch
Manipulation 不触发 没有设置 IsManipulationEnabled 在元素上开启
缩放跳变 把增量当成最终值 累加并限制范围
双指距离总为 0 两个触点位置相同或没有更新 检查触点集合
触屏正常、鼠标无效 Touch 与鼠标是不同输入设备 需要鼠标操作时另写 Mouse 处理

5.10 小练习

  1. 把缩放范围改成 0.8 到 1.2，观察手感。
  2. 增加两指旋转角度，先只显示角度，不修改对象。
  3. 在触屏上画两个触点的移动轨迹。
  4. 把触点数量、距离、缩放值写入日志，排查手势不稳定的问题。

外层 Preview 仍执行 拦截点在它之后，无法倒回阻止
取消拦截仍不执行 检查其他处理器是否设置了 Handled
事件处理器执行两次 检查 XAML 和代码是否重复订阅

键盘输入

问题 检查点
快捷键不生效 是否在 PreviewKeyDown 处理
中文输入不完整 是否只依赖 KeyDown
修饰键判断错误 是否读取 Keyboard.Modifiers
输入框无法输入 是否无条件设置了 e.Handled

拖放

问题 检查点
目标不响应 AllowDrop 是否为 true
光标显示禁止 DragEnter 是否设置了 e.Effects
Drop 没有数据 数据格式字符串是否一致
拖动源没有反应 是否超过系统拖动阈值

触摸

问题 检查点
多指覆盖 是否按 TouchDevice.Id 保存
Manipulation 不触发 是否设置 IsManipulationEnabled
缩放跳动 是否把增量当最终值
触点丢失 是否捕获并正确释放触点

综合练习

练习一：做一个安全的快捷键面板

要求：

  1. 只拦截 Ctrl+S。
  2. 拦截后显示“模拟保存成功”。
  3. 记录操作时间。
  4. 关闭拦截开关后，恢复输入框默认行为。

练习二：做一个拖放排序区

要求：

  1. 左侧有多个卡片。
  2. 拖到右侧时显示允许放置。
  3. 放置后保留卡片名称。
  4. 不支持的数据格式显示拒绝状态。

练习三：做一个触摸缩放画布

要求：

  1. 单指拖动对象。
  2. 双指缩放对象。
  3. 缩放范围限制在合理区间。
  4. 没有触屏时，用按钮模拟缩放。

练习四：做一次输入链路复盘

要求：

  1. 分别记录键盘、拖放和触摸的日志。
  2. 在日志中写清事件阶段、对象名称和关键状态。
  3. 找出一次操作中重复执行的处理器。
  4. 把能抽出的判断移到 InteractionRules。

结语

这一篇的五个主题最终都在回答同一个问题：输入怎样安全、清楚地变成界面行为。

路由拦截决定事件是否继续传递；拦截后的逻辑负责把控制权转成可解释的业务结果；键盘事件处理按键和文本；拖放事件把数据从一个控件交给另一个控件；触摸和 Manipulation 把多根手指变成可计算的状态。
