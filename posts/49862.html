实际界面里三者经常混用。例如一个「图标 + 标题 + 操作按钮」的列表行：

中间列写成 *，标题变长时不会挤压两边的图标和按钮。

1.4 SharedSizeGroup：让不同 Grid 的列对齐

星号列只能在自己的 Grid 内部起作用。如果上下两块内容分属两个 Grid，它们的 Auto 列宽度会各算各的，看起来就参差不齐：

两行的标签宽度不同，第二列起点就不在一条竖线上。SharedSizeGroup 可以把两列绑成一组，取组内最大值：

使用 SharedSizeGroup 有两个前提：

  1. 组名必须完全一致，大小写敏感。
  2. 必须有一个祖先元素设置 Grid.IsSharedSizeScope="True"，它管着这一片区域的共享计算。

注意：参与共享的列必须是 Auto。把 * 放进共享组不会得到期望的结果，因为星号列本来就要吸收剩余空间。

1.5 UniformGrid：把格子平均分给子元素

Grid 需要你手写每一列每一行。如果只是想把空间平均分给若干子元素，用 UniformGrid 更省事：

UniformGrid 的特点：

  • 每个格子宽度相同、高度也相同。
  • 写了 Columns 就按列数排，写了 Rows 就按行数排，两个都写时以 Columns 优先。
  • 子元素数量超过格子数时，会自动增加行或列。
  • 格子之间没有间距属性，间距靠子元素的 Margin 实现。

UniformGrid 只按「格子」考虑，不考虑内容大小。如果每个格子里装的是长度不一的文字，格子仍然一样大，文字会换行或被裁切。这一点和第 1.2 节的星号列有本质区别：

容器 分配依据 适合场景
Grid + 星号列 你指定的权重 需要精确控制比例
UniformGrid 完全平均 卡片墙、缩略图、色块
WrapPanel 按子元素自身尺寸排列，放不下就换行 不定数量的标签、卡片

2.7 计算属性不通知界面怎么办

Department.Count、TotalSalary、AverageSalary 都是没有 set 的计算属性。它们本身不会发通知。

所以在两种情况下统计会不刷新：

  1. 成员集合里增删了员工。
  2. 某个员工的工资改了。

3. 集合数据类型的绑定与数据呈现

本节目标

学完本节，你应该能够：

  • 说清 ObservableCollection<T> 和 List<T> 在绑定上的区别。
  • 用 ItemsControl、ListBox、DataGrid 呈现同一份集合。
  • 用 ICommand 让按钮驱动集合变化。
  • 理解「集合通知」和「对象通知」是两件事。
  • 在集合增删改后让统计数字同步刷新。

3.1 为什么必须用 ObservableCollection

把 List<Employee> 绑到 ListBox，界面能显示数据，但新增一项不会出现在界面上。原因是 List<T> 没有变化通知机制。

ObservableCollection<T> 实现了 INotifyCollectionChanged。集合每发生一次增删，都会发出通知，绑定系统收到后更新界面：

两者的差别可以记成一句话：

ObservableCollection<T> 在命名空间 System.Collections.ObjectModel 下。它同样支持 Add、Remove、Insert、Clear，用法和 List<T> 基本一致。

3.2 集合通知和对象通知是两件事

这一点是初学者最容易混淆的。看下面两种操作：

操作 需要谁发通知 依赖的接口
往集合里 Add 一个新员工 集合 INotifyCollectionChanged
改某个已有员工的 Salary 员工对象 INotifyPropertyChanged

ObservableCollection<Employee> 只负责「集合成员变了」。集合里某个员工的属性变化，它完全不知道，也不会转发。所以 Employee 必须自己实现 INotifyPropertyChanged。

两者配合起来，界面才能做到：新增一行立刻出现，改工资立刻刷新数字。

场景 集合用 元素用
列表固定不变，只改属性 List<T> 也可以 INotifyPropertyChanged
列表会增删，属性也可能变 ObservableCollection<T> INotifyPropertyChanged
只读展示、从不变化 List<T> 也可以 普通属性也可以

4.2 先给数据一个可比较的字段

4.8 为什么不用事件处理做这件事

如果用 ValueChanged 事件，每次拖动都要：

  1. 读取新工资。
  2. 判断落在哪个区间。
  3. 找到对应的视觉元素。
  4. 手动改它的背景色和前景色。

而触发器版本把「什么条件下变成什么样」声明在 XAML 里，数据一变外观自动跟上，代码里一行判断都不用写。

这也是 WPF 的一个核心思路：把「状态与外观的对应关系」声明出来，而不是在代码里一步步地改。

5.1 什么时候需要换整套模板

第 4 章的触发器只改属性，模板结构不变。但有些需求是结构层面的：

  • 主管的卡片要显示「主管」标签、蓝色描边、更大的字号。
  • 普通成员的卡片只是简单的白底一行。

结构不同时，用 Setter 一个个改属性会越来越笨重。这时应该准备两套完整的模板，让程序在运行时决定用哪一套。

这正是 DataTemplateSelector 的用途。

5.2 模板选择器和模板触发器的分工

对比项 数据模板触发器 数据模板选择器
模板数量 一套 多套
决策位置 XAML 里声明 C# 里判断
能改什么 已命名元素的属性 整套结构
适合场景 只换颜色、粗细、可见性 结构差异大
判断复杂度 简单相等/组合条件 任意 C# 逻辑

两者可以叠加使用：选择器选出「主管模板」，主管模板内部再用触发器按工资区间换颜色。

5.6 选择器什么时候被调用

这是最容易困惑的一点。SelectTemplate 在每个数据项第一次生成容器时被调用一次，结果会被缓存。

所以：

  • 修改 IsManager 后，界面不会自动重新调用选择器。
  • 集合增删、滚动导致容器重新生成时，才会再次调用。

在示例项目里能看到这个现象：勾选或取消勾选「主管」复选框后，上方的卡片不会立刻换模板。

要让模板立即切换，常用的三种办法：

办法 做法 适用场景
刷新集合视图 CollectionViewSource.GetDefaultView(Employees).Refresh() 想全部重新生成
换掉 ItemsSource 重新赋值同一个集合的包装 数据量不大
改用模板触发器 用 DataTrigger 改属性而非换模板 结构差异小

如果确实需要「改属性就换整套模板」，通常说明这个需求更适合用触发器实现。选择器更适合数据本身相对稳定、结构差异大的场景，比如不同类型的消息卡片、不同类型的节点。

9 打开页签「5 模板选择器」 三名主管使用蓝色模板
10 打开页签「6 直方图」 四根柱子计数 1、3、2、2

如果某一步结果不对，先在「输出」窗口里找绑定错误。绝大多数「界面没反应」都是绑定路径写错，而不是控件本身有问题。

综合练习

练习一：可搜索的员工看板

要求：

  • 顶部一个搜索框，输入关键字后列表只剩匹配的员工。
  • 关键字同时匹配姓名和部门。
  • 搜索框清空后恢复全部数据。
  • 搜索结果仍然使用第 5 章的选择器渲染。

提示：在 ViewModel 里加 SearchText 属性和 FilteredEmployees 派生属性，SearchText 变化时通知 FilteredEmployees。

练习二：可配置的直方图

要求：

  • 区间边界不再写死在代码里，而是由界面上的两个滑块控制（最低分界、最高分界）。
  • 柱子数量随分界变化自动调整。
  • 柱子颜色按人数多少深浅变化。

提示：把区间划分逻辑抽成一个方法，参数是分界值数组；UniformGrid 会自动适应柱子的数量。

练习三：三层联动的主从视图

要求：

  • 第一层：部门列表。
  • 第二层：该部门的员工列表，按工资降序排列。
  • 第三层：选中员工的详细表单，改动后列表和直方图都同步更新。
  • 顶部显示当前部门的汇总信息。

提示：排序用 CollectionViewSource 或 ListCollectionView 的 SortDescriptions；汇总信息可以放在 Department 上，但要记得手动通知。

结语

这一篇的六章可以压缩成六句话：

章节 一句话
尺寸均分 宽度交给容器算，不要手写像素
多区域整合 一个区域的选中项，就是另一个区域的数据源
集合绑定 集合用 ObservableCollection，元素用 INotifyPropertyChanged
模板触发器 一套模板，按数据值换外观
模板选择器 多套模板，让 C# 决定用哪套
直方图案例 原始集合先统计成区间集合，再交给模板渲染

再往深处走，会碰到虚拟化、CollectionViewSource、数据校验、异步加载等话题。但基础打牢之后，那些内容都只是在这套骨架上的扩展。

动手顺序建议：先把第 1 章的星号列和 UniformGrid 跑通，再加第 2 章的三个区域，然后补第 3 章的集合与命令，最后做第 4、5、6 章的外观和图表。每完成一步都运行一次，看到变化再继续。

祝学习顺利。
